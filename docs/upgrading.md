# Upgrading

## To 0.6

0.6 adds passkeys and API keys, lets a user have several sign-in methods, makes the settings of each method explicit, makes the first admin with `INITIAL_ADMIN_EMAIL` instead of the command line, calls the authenticator app `authenticator` instead of `totp`, and names the calls that open madAuth's dialog after it. What changes for you:

- **The calls that open madAuth's dialog say so.** Rename them; there are no aliases. The calls of `Madauth.password`, `Madauth.passkey` and the other methods (e.g. `Madauth.password.signIn()`) keep their names: they only talk to the server.

  | Before | Now |
  | --- | --- |
  | `Madauth.signIn(options)` | `Madauth.showSignInDialog(options)` |
  | `Madauth.setUpAuthenticator()` | `Madauth.showSetUpAuthenticatorDialog()` |
  | `Madauth.setUpSms()` | `Madauth.showSetUpSmsDialog()` |
  | `Madauth.setUpPasskey()` (new in 0.6) | `Madauth.showSetUpPasskeyDialog()` |
  | `Madauth.manageSignInMethods()` (new in 0.6) | `Madauth.showManageSignInMethodsDialog()` |

- **The command line's admin commands are gone:** `set-roles`, `get-roles`, `set-claims`, `get-claims`, `set-methods`, `get-methods`, `set-password-rules`, `get-password-rules` and `create-user`. They did what the admin API does: admins call `Madauth.admin.setClaims`, `getClaims`, `setSettings` and `getSettings` from your app (e.g. the demo's admin panel) or `POST /auth/admin/*`. Where the steps for earlier versions below name these commands, use the admin API instead. `init`, `start`, `generate-key`, `generate-webhook-secret` and `schema` stay.
- **New: `INITIAL_ADMIN_EMAIL`** makes the first admin: the user who signs in with that address, once it is proven (confirmed by e-mail, or verified by Google or GitHub), gets `admin` in their `roles`, and the webhook gets `user.claims_changed` with `by: "INITIAL_ADMIN_EMAIL"`. Once per value: a value that was applied does nothing afterwards, and a new value applies again, which is the way back in when the only admin is locked out. Existing admins keep their role; a deployment without one sets the variable. `init` asks for it (`--initial-admin-email`), and the AWS template takes it in `cdk.json` under `environment`, a map of environment variables. See [The first admin](server.md#the-first-admin).
- **No admin takes the role from themselves.** `POST /auth/admin/claims/set` refuses to take `admin` from the admin who calls it, and `POST /auth/account/delete` refuses to delete a user who has the role: `403 own_admin_role` (a new error code in the web library). Another admin does it. Give a second user the role.
- **The authenticator app is `authenticator`, not `totp`.** Upgrade the server and `@madauth/web` together: there are no aliases for the old names, so a web library before 0.6 can't reach the app's routes on a 0.6 server. "TOTP" stays only where the algorithm is meant: the `otpauth://totp/…` URI of the QR code, and `amr: ["…", "otp"]`. Update your receiver's checks of `method` and `secondFactor` (the aws-ses-mailer and the dev-receiver of [madAuth-webhooks](https://github.com/inouiw/madAuth-webhooks) name `authenticator` from their next version), your custom screen, your CSS and your configuration:

  | Before | Now |
  | --- | --- |
  | `totp`, the method's id: in the settings (`setSettings`, `getSettings`), `GET /auth/config`, `factors`, `pendingStep`, `GET /auth/methods`, `LoginMethodId`, `MethodId`, `SecondFactor`, and the webhooks' `method`, `secondFactor` and `methods` (`user.signing_up`, `user.signed_up`, `user.signed_in`, `user.email_verified`, `user.second_factor_enabled`, `user.second_factor_disabled`, `email.send_already_registered`, `email.send_password_reset_no_password`) | `authenticator` |
  | `POST /auth/totp/*` and `GET /auth/totp/status` | `/auth/authenticator/*` |
  | the error `totp_required` | `authenticator_required` |
  | the error `totp_setup_required` | split by what is set up: `second_factor_setup_required` when a `required` policy asks for a second factor the user doesn't have (they choose one of `factors`), `authenticator_setup_required` for the sign-up with the app alone after the address is confirmed (`factors: ["authenticator"]`), as `passkey_setup_required` is for the sign-up with a passkey alone |
  | `#madauth_next=totp`, `#madauth_next=totp-setup`, `madauth_factors=totp,…` | `authenticator`, `second-factor-setup`, `madauth_factors=authenticator,…` |
  | `Madauth.totp` | `Madauth.authenticator` |
  | `new Totp()` | `new Authenticator()` |
  | `TotpApi`, `TotpPolicy`, `TotpSetup`, `TotpSignUpOptions`, `SignInWithTotpOptions` | `AuthenticatorApi`, `AuthenticatorPolicy`, `AuthenticatorSetup`, `AuthenticatorSignUpOptions`, `SignInWithAuthenticatorOptions` |
  | the dialog's form classes `totp`, `totp-code`, `totp-setup` (see [Styling](styling.md)) | `authenticator`, `authenticator-code`, `authenticator-setup` |
  | the setup cookie `madauth_totp_setup` | `madauth_authenticator_setup`, sent to `/auth/authenticator` |
  | `TOTP_ISSUER` (and `totpIssuer` in `MadauthConfig`) | `AUTHENTICATOR_ISSUER` (`authenticatorIssuer`); a server with `TOTP_ISSUER` set refuses to start and names the new variable |
  | `init --totp`, `--no-totp` | `--authenticator`, `--no-authenticator` |
  | `docs/totp-security.md` | [`docs/authenticator-security.md`](authenticator-security.md) (the old page only links there) |

  **Stored data stays as it is.** A methods list an earlier madAuth saved with `totp` is read with `authenticator` in its place, and saved with it the next time an admin changes it; so is a pending sign-up's `user.signUpMethod` saved as `totp`. The users' apps keep working: their accounts keep the key `totp:<userId>`, so the store needs no migration. A sign-in that waits for its second step while you upgrade starts again.
- **Each method's settings are explicit.** In `Madauth.admin.setSettings` and `POST /auth/admin/settings/set`, every listed method has both `allowAsSignInMethod` (whether it signs in on its own) and `secondFactor` (its policy); `{}`, `true` and a method with only `secondFactor` are refused with `invalid_settings`. Write `{ password: { allowAsSignInMethod: true, secondFactor: 'optional' } }` instead of `{ password: { secondFactor: 'optional' } }`. `getSettings` answers `allowAsSignInMethod` and `secondFactor` for every method, the app and SMS codes included, and lists `passkey`. See [Sign-in methods](server.md#sign-in-methods).
- **A second factor a policy asks for must be on.** The authenticator app used to be a second factor whenever a policy asked for one, listed or not. Now it is one only when `authenticator` is listed: `authenticator: { allowAsSignInMethod: false, secondFactor: 'none' }` for the app as a second factor only. A list without a second factor that is on, but with a policy, is refused. **The list stored by an earlier madAuth keeps its meaning** (the app a second factor wherever a policy asked for one, `sms` a second factor), so nothing changes until an admin saves a new list, except for the app (`totp` in that list) listed on its own, see the next point.
- **The app signs in on its own for every user who has one, when it is allowed as a sign-in method.** Before, it signed in alone only the users who signed up with it, also with `totp` listed. Now `allowAsSignInMethod: true` lets everyone who set it up sign in with the e-mail address and a code alone, also those who set it up as the second factor of their password; `allowAsSignInMethod: false` lets nobody. **A stored list (from an earlier madAuth) with `totp` on its own next to other methods** means neither, so until an admin saves the methods again, the app is a second factor only, and the server's log says so once: users who signed up with the app alone can't sign in until you allow it. To choose, save the methods with `Madauth.admin.setSettings`: `authenticator: { allowAsSignInMethod: false, secondFactor: 'none' }` keeps the app a second factor, `allowAsSignInMethod: true` lets everyone with the app sign in with it alone. Where nothing but the app signs in, it keeps signing in. A list without `totp` works as before.
- **A user can have several sign-in methods.** A signed-in user adds a passkey, a password, the e-mail link, Google or GitHub, and removes one that isn't their last way in: see [Several sign-in methods](sign-in-methods.md). A sign-in with a method the user doesn't have is still refused (`other_method`): methods are added only while signed in. `only_method` now means "the user's last way to sign in", for the app as for every other method, and `required_by_policy` lets a factor go when the user keeps another one (a passkey counts).
- **New: passkeys**, a method with the id `passkey`: `new Passkey()`, `Madauth.passkey`, `Madauth.showSetUpPasskeyDialog()`, `POST /auth/passkey/*`, `passkey` in `GET /auth/config` and in the settings, `PASSKEY_RP_ID` (optional), `amr: ["passkey"]`, and the errors `passkey_required`, `passkey_unknown` and `passkey_unsupported`. It comes first in `loginMethods`, and the dialog shows its "Sign in with a passkey" button above the others. Off until an admin lists it. Allowed as a sign-in method on a server that confirms addresses by e-mail, it also signs people up alone: `Madauth.passkey.signUp`, `POST /auth/passkey/signup`, `passkey.signUp` in `GET /auth/config`, and "Use a passkey instead of a password" on the dialog's "Create account" form; it then counts as a method that creates users. Confirming the address of such a sign-up answers with the new error `passkey_setup_required` (`#madauth_next=passkey-setup` for a redirect); the dialog handles it, a custom screen calls `Madauth.passkey.add()`. See [Passkeys](server.md#passkeys).
- **New: managing methods.** `Madauth.showManageSignInMethodsDialog()` opens the dialog on the user's methods; `Madauth.methods.list()` and `remove(id)`, `Madauth.password.add()`, `Madauth.emailLink.add()`, and `purpose: 'link'` for the Google and GitHub buttons do it on a custom screen. `GET /auth/methods`, `POST /auth/methods/remove`, `POST /auth/password/add`, `POST /auth/email-link/add`, `POST /auth/google/link` and `/start?link=1` of the redirect flows (which return with `#madauth_linked=…`, reported as `linked` by `Madauth.initialize`). New errors: `reauth_required` (changing a method takes a sign-in within the last ten minutes), `account_taken`, `already_added`, `method_not_found`, `forbidden_origin`.
- **One reset replaces the removal of a lost factor.** `remove-totp` and `remove-sms` on the command line, `POST /auth/admin/totp/remove` and `POST /auth/admin/sms/remove`, and `Madauth.admin.removeAuthenticator` are gone. A user who lost a second factor, or every way in, is reset by an admin instead: `Madauth.admin.resetSignIn(email)` (`POST /auth/admin/sign-in/reset`) removes all their methods and second factors, ends their sessions and marks the address unconfirmed; they sign up again and keep their id, claims and roles. There is no command for it: an admin who lost their own way in is reset by another admin, and with no admin who can sign in, a new `INITIAL_ADMIN_EMAIL` value makes one. Check who is asking before a reset: afterwards the address is all it takes. An admin's reset sends `user.sign_in_reset` (opt in with `WEBHOOK_EVENTS`), so `user.second_factor_disabled` no longer carries `by`. See [Resetting a user's sign-in](server.md#resetting-a-users-sign-in).
- **New webhook types `user.method_added` and `user.method_removed`** (opt in with `WEBHOOK_EVENTS`). `user.signed_in` can carry `method: "passkey"` and `secondFactor: "passkey"`; `user.signing_up`, `user.email_verified` and `user.signed_up` can carry `method: "passkey"`, and `email.send_already_registered` and `email.send_password_reset_no_password` can list `passkey` in `methods`.
- **The second step can be a passkey.** Besides `authenticator_required` and `sms_required`, a sign-in can end with `401 passkey_required` (a passkey comes first of the user's factors), and `second_factor_setup_required` names in `factors` what the user can set up: `["passkey", "authenticator", "sms"]`, as the methods that are on allow; it used to be `[]`. The redirect flows can return with `#madauth_next=passkey`. The dialog handles all of it; a custom screen handles `passkey_required` with `Madauth.passkey.verify()` (or the user switches to a factor in `factors`), and offers `Madauth.passkey.add()` at the setup when `factors` has `passkey`.
- **`MADAUTH_KEY_SERVICE` is required.** It says where madAuth keeps its keys, and the server doesn't start without it. To keep your `MADAUTH_SIGNING_KEY`, set `MADAUTH_KEY_SERVICE=local` (madAuth then warns at every start that the keys are in its memory). `MADAUTH_KEY_SERVICE=aws-kms` keeps them in AWS KMS, where they never leave it: create the keys with `npx @madauth/server kms-setup`, give the server's role the policy it prints, rotate them daily with `kms-rotate`, and remove `MADAUTH_SIGNING_KEY`. The move signs everyone out and makes the authenticator apps and recovery codes set up before stop working. `init` writes `MADAUTH_KEY_SERVICE=local`; the AWS template sets it too. See [Key service](server.md#key-service).
- **The signing key can be rotated.** `MADAUTH_SIGNING_KEY` also takes a set of keys, the newest first (`{"keys":[<new>,<old>]}`): the newest signs, and the others still verify sessions and read what was stored under them. `/.well-known/jwks.json` lists every key of the set, so a backend that verifies sessions with one fixed public key instead of the published list (as `createSessionVerifier` does) must take each of them. A deployment that keeps its one key changes nothing. See [Rotating the signing key](server.md#rotating-the-signing-key).
- **`createApp` with a configuration of your own:** `MadauthConfig.signingKey` is now `keyService`, through which madAuth signs, hashes and encrypts; `createLocalKeyService([jwk])` makes the built-in one from your key, and `loadConfig` sets it from `MADAUTH_SIGNING_KEY`.
- **New: API keys.** A signed-in user makes keys for programs that call your API or madAuth's admin API in their name (`Authorization: Bearer madauth_…`), each limited to scopes: `Madauth.apiKeys`, `Madauth.showManageApiKeysDialog()`, `Madauth.admin.listApiKeys` and `revokeApiKey`, `GET /auth/api-keys/scopes`, `GET /auth/api-keys`, `POST /auth/api-keys/create`, `revoke` and `verify`, `POST /auth/admin/api-keys/list` and `revoke`, `createApiKeyVerifier` in `@madauth/server/verify` for your backend, `API_KEY_SCOPES_URL` (optional) for your app's scopes, the webhook types `user.api_key_created` and `user.api_key_revoked` (opt in with `WEBHOOK_EVENTS`), `byApiKey` in `user.claims_changed` and `user.sign_in_reset`, and the errors `invalid_scopes`, `scope_not_allowed`, `too_many_api_keys` and `api_key_not_found`. POST requests with an `Authorization` header no longer need an allowed `Origin`. Nothing changes until users make keys. See [API keys](api-keys.md).
- **Sessions carry `auth_time`**, when the user signed in, kept across renewals. Sessions from before the upgrade have none, so their users sign in again before they change a method.
- **Schema version 10.** `account.name`, `account.credentialId`, `account.signCount`, `account.transports` and `account.lastUsedAt` for passkeys (version 8), `user.signUpMethod`, the method a pending sign-up confirms its address for (version 9), and the new model `apiKey` (version 10). SQLite upgrades itself and DynamoDB needs nothing; for your own SQL tables run `npx @madauth/server schema --dialect <yours> --from 7` and apply it before you deploy. `account.primaryUserId` stays unique, but marks only the account a user signed up with.
- **The dialog's texts:** `only_method` says "This is the only way you sign in" instead of naming the authenticator app, and the setup of a second factor names the methods that ask for it as in a sentence ("signing in with Google or a password also asks for a code from the app") instead of by their buttons ("Continue with Google and Email & password").

## To 0.5

0.5 adds GitHub sign-in (`github`), the passwordless e-mail link, a primary sign-in method with the id `email-link`, and SMS codes as a second factor next to the authenticator app (`sms` in the settings). It renames the webhook types so the name says what a call is, tells you when a sign-up is complete, and gives every user one sign-in method. What changes for you:

- **New: GitHub sign-in**, a primary sign-in method with the id `github`, through GitHub's redirect flow: `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET` from a GitHub OAuth App (see [GitHub OAuth App setup](server.md#github-oauth-app-setup)), `new GitHub()` and `Madauth.github` in the web library, `GET /auth/github/start` and `callback`, `github` in `GET /auth/config` and in the settings (`set-methods github=optional`, `Madauth.admin.setSettings`) with a `secondFactor` policy like Google, `init --github-client-id` and `--github-client-secret`, and `amr: ["github"]`. `user.signing_up`, `user.signed_up` and `user.signed_in` can carry `method: "github"`, and `email.send_already_registered` and `email.send_password_reset_no_password` can list `github` in `methods`; the receivers of [madAuth-webhooks](https://github.com/inouiw/madAuth-webhooks) name it from their next version, an older one names the id as it is. The server keeps the GitHub access token on the account, encrypted with a key derived from `MADAUTH_SIGNING_KEY`, to revoke the OAuth App's authorization when the user deletes their account.
- **Switch the new methods on if you have listed the methods.** GitHub and the e-mail link are on by themselves only until an admin lists the methods (`set-methods` or `Madauth.admin.setSettings`). A list saved with an earlier madAuth leaves them out, so they stay off, and `GET /auth/config` reports `github: null` / `emailLink: null` although the server has what they need. Add them to your list: `set-methods` replaces the whole list, so run `get-methods` and repeat what it prints with `github` and `email-link` added (e.g. `set-methods google password=required totp sms` becomes `set-methods google github password=required totp email-link sms`).
- **The dialog opens by itself after a sign-in that failed outside it.** With `ui: 'dialog'` and nobody signed in, it opens with the error after a failed redirect sign-in (Google's code flow, GitHub), a confirmation or sign-in link that failed, or a One Tap sign-in the server refused (e.g. `other_method`). Before, the error waited until the next `Madauth.signIn()`. `initialize` still reports the failure; a page that showed it itself, or called `Madauth.signIn()` for it, can drop that. With `ui: 'custom'` nothing changes.
- **The redirect flows name their method.** `GET /auth/google/callback` (and GitHub's) add `madauth_method=google` / `github` to the hash next to `madauth_error` and `madauth_next`, so the web library tells the providers apart; without it (a server before 0.5) the library assumes Google. Upgrade `@madauth/web` together with the server: a library before 0.5 leaves `#madauth_method=…` in the address bar after a redirect return (harmless, but it ends up in bookmarks). The dialog's texts that said "instead of Google" now name the provider that was refused (`other_method`), and the "forgot password" hint names the providers you offer.

- **Webhook types are renamed.** Update your receiver and `WEBHOOK_EVENTS` together; a server whose `WEBHOOK_EVENTS` still has an old name refuses to start and names the new one. The aws-ses-mailer and the dev-receiver need the new names too.

  | Before | Now |
  | --- | --- |
  | `email.verify` | `email.send_verification` |
  | `email.reset` | `email.send_password_reset` |
  | `email.already_registered` | `email.send_already_registered` |
  | `email.no_password` | `email.send_password_reset_no_password` |
  | `signup.before` | `user.signing_up` (same data and answer) |
  | `user.created` | gone: see `user.signed_up` |
  | `email.verified` | `user.email_verified`, now with `method` (`password`, `totp` or `email-link`) |
  | `email.password_reset` | `user.password_reset` |
  | `totp.enabled`, `totp.disabled` | `user.second_factor_enabled`, `user.second_factor_disabled` with `method: "totp"` (and `by` when an admin removed it) |
  | `totp.recovery_code_used` | `user.recovery_code_used` |

  `user.claims_changed` carries `user` (with the new claims) instead of `userId` and `email`. `user.signed_in`, `user.deleted` and `user.claims_changed` keep their names.
- **New webhook type `user.signed_up`** (`user`, `method`): sent once per user, at their first session, when they have their sign-in method and every second factor its policy requires. `user.created` came before the address was confirmed, for sign-ups that might never be finished or might be someone else's; act on `user.signed_up` instead. A user whose sign-up was complete before the upgrade never gets it; one started before it gets it when it is finished (or started again and finished) after.
- **A user has one sign-in method.** The authenticator app signs in alone only for users who signed up with it; for a password, Google or e-mail link user it is a second factor and never a way in by itself, also while `totp` is on. Such a user who signed in with the app alone before now gets `invalid_credentials` there and uses their method with the code. They can remove the app whatever methods are on (`only_method` is only for the app a user signed up with), and the setup screen no longer says the app signs them in on its own (`totpSetup.effects.standalone` is gone from the strings). Users from before 0.4 who have both a password and Google keep both.
- **Schema version 7.** `account.primaryUserId` (unique: the user's id on the account they sign in with, empty for a second factor), `account.secondFactor` and `user.signedUpAt`. Existing records need no change. SQLite upgrades itself and DynamoDB needs nothing; for your own SQL tables run `npx @madauth/server schema --dialect <yours> --from 6` (or from the version you have) and apply it before you deploy. A custom adapter must allow many records with an empty unique field: `storeAdapterContract` checks it.

- **New webhook type `email.send_signin_link`** (the e-mail with the sign-in link and code; the link lives 15 minutes): the method is configured exactly when it is in `WEBHOOK_EVENTS`, and on until an admin lists the methods. Update your receiver first: the aws-ses-mailer answers 400 to an `email.*` type it doesn't know, so the server would report `temporarily_unavailable`, and the dev-receiver prints such a call without its link. `user.signing_up`, `user.signed_up` and `user.signed_in` can carry `method: "email-link"`; `email.send_already_registered` can list it in `methods`.
- **New:** `new EmailLink()` and `Madauth.emailLink` in the web library, `POST /auth/email-link/send` and `verify`, `emailLink` in `GET /auth/config`, `email-link` in the settings (`set-methods email-link=optional`, `Madauth.admin.setSettings`) with a `secondFactor` policy like Google and password, `init --email-link`, and `amr: ["email"]`.
- **The placeholder id `email` is now `email-link`** in `LoginMethodId` and `loginMethods` (it was never listed), and `sms` is gone from them: SMS codes are a second factor, not a row in the dialog. `Google` sign-in refuses a link user's address with `other_method`, and `methods` there may say `email-link`.
- **Schema version 6.** `account.phone` for the phone number of SMS codes, and `user.lastSmsAt` for their one-per-minute limit. SQLite upgrades itself and DynamoDB needs nothing; for your own SQL tables run `npx @madauth/server schema --dialect <yours> --from 5` and apply it before you deploy. See [Schema versions](server.md#schema-versions).
- **New webhook type `sms.send_code`** (opt in with `WEBHOOK_EVENTS`; it configures SMS codes, and your receiver has to send the SMS, e.g. through SNS or Twilio). Adding or removing a phone is `user.second_factor_enabled` (with `phone`) or `user.second_factor_disabled` with `method: "sms"`. `user.signed_in` can carry `secondFactor: "sms"`.
- **The second step's answers carry `factors`**, the second factors the user can finish with (`["totp"]`, `["sms"]`, `["totp", "sms"]`, or `[]` before a setup), and a user with a phone only gets `401 sms_required` instead of `totp_required`. The web library handles it by itself: the dialog shows the SMS step, offers "send a code by SMS instead" when the user has both, and "use your phone number instead" at the app's setup when SMS codes are on. A custom screen handles `sms_required` with `Madauth.sms.send()` and `verify()`, and `pendingStep` can be `{ step: 'sms', … }` with `factors`. The redirect flow can return with `#madauth_next=sms` and `madauth_factors=…`.
- **The dialog's English texts write "email"** instead of "e-mail" ("Email", "Email & password", "Email link", …), the links between sign-in and sign-up read "No account? Create one" and "Already have an account? Sign in", and the address field next to a password has `autocomplete="username"`. The sign-up form shows Google's button too (when Google is on) and puts the optional name last, password fields have an eye button that shows the password, and each new view moves the focus to its first field (or its heading). Tests or screenshots that look for the old texts need updating.
- **The challenge cookie moved** from `/auth/totp` to `/auth`, so the SMS routes receive it. Nothing to do; a cookie from before the upgrade expires within ten minutes.
- **New:** `Madauth.sms` and `Madauth.setUpSms()`, `POST /auth/sms/*`, `POST /auth/admin/sms/remove` and `remove-sms` on the command line, `sms` in `GET /auth/config` and in the settings (`set-methods … sms`, `Madauth.admin.setSettings`), `init --sms`, `amr: ["…", "sms"]`, and the errors `sms_required`, `invalid_phone`, `no_phone` and `too_soon`. `Madauth.totp.remove` is allowed under a `required` policy when the user keeps a phone (and `Madauth.sms.remove` when they keep the app); the message of `required_by_policy` says "a second factor" now.

## To 0.4.0-beta.2

- **The dialog lists only the methods that are on.** A method is listed when its provider is passed to `Madauth.initialize` and the server offers it; methods without one (e.g. E-mail link and SMS code) no longer show up as "coming soon". `<madauth-login>`'s `open()` now waits until madAuth is ready before the dialog shows, so it never fills in while open; when madAuth isn't initialized or couldn't reach the server, the dialog shows the error and no method buttons. The plain "Continue with Google" button the dialog showed without a Google provider is gone; with one, Google's own button is shown as before. Tests or screenshots of your page that rely on the placeholder buttons need updating.
- **Password rules are a setting.** `PASSWORD_MIN_LENGTH` is gone, and a server that still has it refuses to start, so a stricter minimum is never lowered without notice. Remove it and set the minimum with `npx @madauth/server set-password-rules min-length=<n>` (needs only `DATABASE_URL`) or `Madauth.admin.setSettings({ password: { minLength } })`. See [Password rules](server.md#password-rules).
- **Easy-to-guess passwords are refused.** New passwords (sign-up, reset, `create-user`) also need a zxcvbn strength score of at least 2 by default, which refuses common passwords like `password1234`. Existing passwords keep working. To check the length only, as before, run `set-password-rules min-score=0`.
- `GET /auth/config`, `Madauth.password.policy` and the admin settings have `minScore` next to `minLength`, and a `weak_password` error has `minLength` or `minScore`. `Madauth.admin.setSettings` takes `methods`, `password` or both.

## To 0.4

0.4 adds the authenticator app (TOTP), as a second factor for Google and password and as a method of its own, and a sign-in policy. What changes for you:

- **The settings list what is on.** The `methods` setting is the list of the primary methods that are on (`google`, `password`, `totp`), each with its policy for the authenticator app (`none`, `optional`, `required`); a method that is not listed is off. A value stored by 0.3 is ignored with a warning in the log: run `set-methods` again after upgrading, e.g. `set-methods google password`. `Madauth.admin.setSettings` replaces the list instead of merging into it, and the answer says `configured` instead of `available`, with `secondFactor` for Google and password and a `totp` entry. Until the methods are set, a server runs Google and/or password without a second factor, and the authenticator app on its own is off until listed.
- **Schema version 5.** `account.lastUsedStep`, `account.setupId` and the new model `recoveryCode`. SQLite upgrades itself and DynamoDB needs nothing; for your own SQL tables run `npx @madauth/server schema --dialect <yours> --from 4` and apply it before you deploy. See [Schema versions](server.md#schema-versions).
- **E-mail confirmation moved.** `POST /auth/password/verify-email` is now `POST /auth/email/verify`, and `send-verification` is `POST /auth/email/send-verification`: the confirmation is the same for a sign-up with a password and one with the app. The web library's methods keep their names; only direct HTTP users adjust.
- **Google no longer joins a user who signs in another way.** A Google sign-in with the address of a password user used to link the Google account to them; now it answers `403 other_method`, since whoever controls the Google account must not get past the password (and the app). Users who already have both accounts keep both. A sign-up nobody finished is still taken over.
- **Sign-ins may end in a second step.** With a policy that asks for the app, `password.signIn`, `verifyEmail`, `confirmReset` and Google end with `totp_required` or `totp_setup_required` instead of a user: the dialog handles it, with or without `new Totp()` (which adds the app as a method of its own); a custom screen calls `Madauth.totp.verify` or the setup pair (see [Building your own login screen](custom-ui.md#authenticator-app-madauthauthenticator)). The redirect flow may return with `#madauth_next=…`.
- **`deleteAccount` takes a code** once the user has the app (`Madauth.deleteAccount({ code })`; `code_required` without one).
- **`amr` is exposed:** on `user.amr` in the web library and in `createSessionVerifier`'s result, e.g. `['pwd', 'otp']`. Webhook `user` objects don't carry it.
- **New webhook types** `totp.enabled`, `totp.disabled` and `totp.recovery_code_used` (opt in with `WEBHOOK_EVENTS`); `user.signed_in` can carry `method: "totp"` and `secondFactor`; `signup.before` and `user.created` can carry `method: "totp"`.
- **New:** `TOTP_ISSUER` (optional), `GET /auth/config` with `totp` and `email` fields and `secondFactor` on Google and password, `POST /auth/admin/totp/remove` and `remove-totp` on the command line, `init --totp` for a server where people sign up with the app alone.
- **Keep `MADAUTH_SIGNING_KEY`:** the secrets of the authenticator apps are encrypted with a key derived from it. A new key makes every enrolled app stop working until it is set up again.

## To 0.3.0-beta.2

- **"Forgot password?" only resets passwords.** A user without a password (who signs in with Google) no longer gets a reset e-mail that adds one. Instead madAuth sends the new type `email.no_password`, which tells them how they sign in. Add it to `WEBHOOK_EVENTS` and update your receiver first: the aws-ses-mailer and the dev-receiver of [madAuth-webhooks](https://github.com/inouiw/madAuth-webhooks) handle it from their next version, while an older mailer answers an empty 2xx to a type it doesn't know, so the server would count the e-mail as sent. Without the type in the list, such a user gets no e-mail, and the answer comes faster than for an address with a password (see [Password security](password-security.md#no-account-enumeration)).
- **`email.already_registered` carries `methods`**, how the user signs in (e.g. `["google"]`), so the e-mail can say so instead of pointing a Google user to "Forgot password?".
- **`Madauth.initialize` resolves with `leftOut`**, the methods whose providers the server doesn't offer, on success and on failure. Code that compares the result as a whole, like `toEqual({ isSuccess: true })`, has to expect `leftOut` as well.

## To 0.3

0.3 stores every user, whichever way they sign in, and replaces roles with claims. What changes for you:

- **`DATABASE_URL` is required**, also for Google-only servers (`sqlite:<path>` or `dynamodb:<table>`, or your own store adapter). E-mail & password sign-in is on when the webhook sends the e-mails (`email.verify` and `email.reset` in `WEBHOOK_EVENTS`), no longer whenever a database is set. A server with a database and no webhook is a Google-only server now.
- **Google users get a new id.** A Google user used to be `google:<sub>`; now every user is `usr_…`, the same whichever way they sign in. Data your backend keyed by the old id belongs to the new one: on the first sign-in after the upgrade, the `user.created` event (with `method: "google"`) carries the new id and the address. Sessions issued before the upgrade end when their session token expires.
- **Roles are a claim.** `user.roles` is gone; the session token and `user` carry `claims`, and roles are `claims.roles`. The `role` table is dropped (schema version 4) and roles are not migrated: set them again with `npx @madauth/server set-roles <email> admin`, after that user has signed in once. `Madauth.admin.setRoles` / `getRoles` became `setClaims` / `getClaims`, and the HTTP routes `/auth/admin/roles/*` became `/auth/admin/claims/*`.
- **Webhook events were renamed:** `password.reset` → `email.password_reset`, `roles.changed` → `user.claims_changed` (its data is `userId`, `email`, `claims`, `by`). `signup.before` and `user.created` are sent for Google sign-ups too, with a `method`. `user.deleted` has no `passwordUserId` any more: the deleted user is `user.id`.
- **Custom store adapters:** run `npx @madauth/server schema --dialect <yours> --from 3` and apply the SQL before you deploy. See [Schema versions](server.md#schema-versions).

See [Claims](server.md#claims) and [Sign-in methods](server.md#sign-in-methods) for what is new.
