Google sign-in flow
In the browser One Tap / FedCM Through the server Redirect

Sets how the Google button in the sign-in dialog works.

Both sign the user in with their Google account; they differ in where Google is talked to. The current one is what the dialog's Google button uses.

In the browser, One Tap / FedCM, new GoogleFedcm(): the browser shows “Continue as …” (One Tap) and hands madAuth Google's ID token, which the madAuth server verifies. No redirect, and the page keeps its state.

Through the server, the redirect flow, new GoogleRedirect(): the browser is redirected to Google and back, and the madAuth server exchanges the code for the token. Works where One Tap doesn't (e.g. some in-app browsers) and needs GOOGLE_CLIENT_SECRET on the server.

This madAuth server isn't configured for the redirect flow: it needs GOOGLE_CLIENT_ID and GOOGLE_CLIENT_SECRET. Until then, the dialog has no Google button.

This madAuth server isn't configured for GitHub sign-in: it needs GITHUB_CLIENT_ID and GITHUB_CLIENT_SECRET from a GitHub OAuth App. Until then, the dialog has no GitHub button.

Admin

        

          For users with the role admin. The first admin is the user who signs in with the server's
          INITIAL_ADMIN_EMAIL; admins give the role to others with setClaims.
        

        
        

          You don't have the role, so these calls answer forbidden.
          
            Visitors don't get it on madauth.com: an admin could change every visitor's claims, reset their sign-in
            and switch sign-in methods off for everyone.
          
          To try the admin API, run the demo on your machine
          and give yourself the role: set INITIAL_ADMIN_EMAIL in packages/server/.env to your
          address, and sign in with it.
